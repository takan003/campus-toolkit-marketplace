# 模組投稿與審核流程（B+）

本市集是靜態 GitHub repo，沒有投稿後台。投稿流程採 **fork＋PR**；任何人都可以投稿，但**審核通過才可標為 `reviewed`（已審核社群）**。

本流程只規範**要上架到 C 的 market 模組**；fork 主人自行開發、放進自己 `src/modules` 的 local 模組不受市集規範約束。

## 狀態

| 狀態 | 意義 | 誰可以設定 |
|---|---|---|
| `official` | 官方模組，信任團隊維護 | 維護者 |
| `reviewed` | 已審核社群模組 | 維護者（需 `signature`＋`publicKey`） |
| `experimental` | 實驗模組，未審核 | 投稿者（fork PR 只能送這個） |

## 投稿者流程

1. 在自己的模組 repo 完成版本，確認 `module.json` 的 `author.version` 與 `changelog[0].version` 一致。
1. 在自己的 repo 打 tag 或留下 commit SHA，供維護者審核。
1. fork `campus-toolkit-marketplace`，clone 到本機。
1. 在 C 執行（`<模組路徑>` 指向你的模組資料夾）：
   ```bash
   npm run submit -- <模組路徑>
   ```
   這會產生 release zip、更新 `index.json`／`site/index.json`／`releases/notes.txt`，但**不會 commit／push**；狀態固定 `experimental`。
1. 檢查 diff，commit 後 push 到自己的 fork，開 PR 到 C。
1. CI 會檢查：
   - `status` 是否為 `experimental`
   - index／release zip／checksum 是否一致
   - `modules/<id>/module.json` 是否與 index 一致
1. 維護者審核通過後，才會把狀態改成 `reviewed` 並合併。

> fork PR 不能自行把狀態改成 `official`／`reviewed`；CI 會直接拒絕。

## 維護者審核流程

1. 先看投稿者提供的模組 repo／tag，確認 PR 的 zip 確實由該版本產生。
1. 對照 `campus-toolkit/AGENTS.md` 與 `docs/模組架構公開前診斷.md` 的最低限度審核清單：
   - import 公開面、`getAdminDb`／`getAuth` 使用
   - `dataCollections` 是否合理，有無碰宿主保留集合
   - 外部網路請求與 `process.env`／金鑰讀取
   - API auth／CSRF／rate limit／module gate
   - 管理頁 `AdminSectionShell`
   - 混淆、動態載入、隱藏檔
1. 在測試主程式 A 掛載並跑 `module:check`、lint、實際操作。
1. 若通過：
   - 在 `index.json` 與 `site/index.json` 把該模組 `status` 改成 `reviewed`。
   - 補上 `signature` 與 `publicKey`（B+ 規定；目前先警告，下一階段強制）。
   - 合併 PR，GitHub Pages 會自動部署。
1. 若不通過：維持 `experimental` 或關閉 PR，並在 PR 留下原因。

## 維護者指令

審核通過後，由維護者用上游分支重新發布（不要在 fork PR 直接標 `reviewed`）：

```bash
npm run publish:push -- <模組路徑> --status reviewed
```

官方模組：

```bash
npm run publish:push -- <模組路徑> --status official
```

## 重要限制

- `reviewed` 在 B+ 政策上要求 `signature`＋`publicKey`；目前 validator 先警告，簽章綁定流程落地後升為強制。
- 已審核模組仍是 in-process，**不是沙箱**；審核與簽章只降低風險。
- `experimental` 只適合測試，不建議學校正式安裝。
