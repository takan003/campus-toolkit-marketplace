# 模組投稿與審核流程（B+）

本市集是靜態 GitHub repo，沒有投稿後台。投稿流程採 **fork＋PR**；任何人都可以投稿，但**審核通過才可標為 `reviewed`（已審核社群）**。

本流程只規範**要上架到 C 的 market 模組**；fork 主人自行開發、放進自己 `src/modules` 的 local 模組不受市集規範約束。

## 治理邊界

1. **C 採 PR 審核制**：外部作者可 fork C、開 PR，但只能送 `experimental`；維護者審核通過才改成 `reviewed`／`official` 並 merge。
1. **模組作者自己的 repo** 的 PR、版本節奏與審核，由作者自行管理；那是作者與其使用者之間的關係，不屬於 C 的治理範圍。
1. **主程式 A** 封閉維護，不接受外部 PR；外部只能 fork A 自行維護。模組要進 A，只有兩條路：正式上架 C 後由學校安裝，或作者放進自己 fork 的 `src/modules`。

## 狀態

| 狀態 | 意義 | 誰可以設定 |
|---|---|---|
| `official` | 官方模組，信任團隊維護 | 維護者 |
| `reviewed` | 已審核社群模組 | 維護者（需 `signature`＋`publicKey`） |
| `experimental` | 實驗模組，未審核 | 投稿者（fork PR 只能送這個） |

## 投稿者流程

1. 在自己的模組 repo 完成版本，確認 `module.json` 的 `author.version` 與 `changelog[0].version` 一致。
1. 在自己的 repo 打 tag 或留下 commit SHA，供維護者審核。
1. fork `campus-toolkit-marketplace`，clone 到本機。
1. 在 C 執行（`<模組路徑>` 指向你的模組資料夾）：
   ```bash
   npm run submit -- <模組路徑>
   ```
   這會產生 release zip、更新 `index.json`／`site/index.json`／`releases/notes.txt`，但**不會 commit／push**；狀態固定 `experimental`。
1. 檢查 diff，commit 後 push 到自己的 fork，開 PR 到 C。
1. CI 會檢查：
   - `status` 是否為 `experimental`
   - index／release zip／checksum 是否一致
   - `modules/<id>/module.json` 是否與 index 一致
1. 維護者審核通過後，才會把狀態改成 `reviewed` 並合併。

> fork PR 不能自行把狀態改成 `official`／`reviewed`；CI 會直接拒絕。

## 作者公鑰與簽章（B+）

1. 作者產生 ed25519 私鑰（私鑰自己保管，不可提交）：
   ```bash
   node ../campus-toolkit/scripts/module-sign.mjs keygen <你的名字>
   ```
   工具會列出公鑰（base64 SPKI）。
1. 作者把「公鑰＋GitHub repo」提供給維護者；維護者確認 repo 權限後登記：
   ```bash
   npm run keys:add -- --author <名稱> --public-key <base64> --repos owner/repo --note "說明"
   ```
   `keyId` 由公鑰 sha256 自動計算，不能手動指定。
1. 投稿時用私鑰對 release zip 的 sha256 簽章，並把 `signature`／`publicKey` 寫進 `index.json` 與 `site/index.json`。
1. 維護者審核通過後，把 `status` 改成 `reviewed`；C 驗證時會檢查：
   - `keys.json` 格式正確、`keyId` 與公鑰相符
   - 公鑰存在於 `keys.json`、作者相符、狀態非 revoked
   - `publicKey` 是釘選公鑰
   - 簽章對當前 zip 的 sha256 成立
1. 常用指令：
   ```bash
   npm run keys:list          # 列出所有公鑰與狀態
   npm run keys:validate      # 驗證 keys.json（CI 也會跑）
   npm run keys:export-trust  # 產生主程式 MODULE_MARKET_TRUSTED_KEYS 的 JSON
   ```
   官方 E／F／G 的公鑰已內建在主程式，`keys:export-trust` 仍會一併列出，方便自架市集同步。

### 公鑰輪替（重疊期）

1. 先新增新金鑰，**不要立刻撤銷舊金鑰**：
   ```bash
   npm run keys:rotate -- --author <名稱> --public-key <新公鑰> --repos owner/repo
   ```
1. 用新私鑰重新簽章所有該作者的模組，重新發布並更新 `index.json`／`site/index.json`。
1. 確認沒有模組還在使用舊金鑰後，撤銷舊金鑰：
   ```bash
   npm run keys:revoke -- --key-id sha256:... --author <名稱>
   ```
1. 執行 `npm run validate`；CI 會用 `keys.json` 重新驗證所有簽章。

### 撤銷與下架

1. 私鑰外洩或作者要求撤銷時：
   ```bash
   npm run keys:revoke -- --key-id sha256:... --author <名稱>
   ```
   指令會列出使用該公鑰的已上架模組。
1. 撤銷後，使用該金鑰的模組會**驗證失敗**（CI 紅燈），不會默默繼續上架。
1. 處置方式：
   - 作者仍可信 → 用新金鑰重新簽章、重新發布。
   - 無法確認安全 → 從 `index.json`／`site/index.json` 移除該模組，並在 README／PR 說明。
1. 已安裝該模組的學校不會自動被刪除；主程式安裝端會在下一次更新／驗章時拒絕，學校需自行卸載或改用新版本。

## 維護者審核流程

1. 先看投稿者提供的模組 repo／tag，確認 PR 的 zip 確實由該版本產生。
1. 對照 `campus-toolkit/AGENTS.md` 與 `docs/模組架構公開前診斷.md` 的最低限度審核清單：
   - import 公開面、`getAdminDb`／`getAuth` 使用
   - `dataCollections` 是否合理，有無碰宿主保留集合
   - 外部網路請求與 `process.env`／金鑰讀取
   - API auth／CSRF／rate limit／module gate
   - 管理頁 `AdminSectionShell`
   - 混淆、動態載入、隱藏檔
1. 在測試主程式 A 掛載並跑 `module:check`、lint、實際操作。
1. 若通過：
   - 在 `index.json` 與 `site/index.json` 把該模組 `status` 改成 `reviewed`。
   - 補上 `signature` 與 `publicKey`（B+ 規定；C 驗證會強制檢查）。
   - 合併 PR，GitHub Pages 會自動部署。
1. 若不通過：維持 `experimental` 或關閉 PR，並在 PR 留下原因。

## 維護者指令

審核通過後，由維護者用上游分支重新發布（不要在 fork PR 直接標 `reviewed`）：

```bash
# 1. 先 dry-run：module-check、必要目錄、敏感檔、zip 內容比對
npm run publish:check -- <模組路徑> --sign-key <ed25519私鑰檔>

# 2. 正式發布
npm run publish:push -- <模組路徑> --status reviewed --sign-key <ed25519私鑰檔>
```

官方模組（`official` 也必須簽章；zip 內容變更時舊簽章不能沿用）：

```bash
npm run publish:push -- <模組路徑> --status official --sign-key <ed25519私鑰檔>
```

`publish` 會自動：

1. 跑宿主 `module:check`（找不到時要求加 `--skip-check`）
2. 檢查必要目錄與機密檔（`.env*`、`*.key`、`*.pem` 等）
3. 壓縮後解開 zip，比對 `module.json` 與來源、檢查禁用目錄
4. 檢查 500KB 上限與 checksum
5. `official`／`reviewed` 若內容變更但沒有 `--sign-key`，直接拒絕

## 重要限制

- `reviewed` 必須提供 `signature`＋`publicKey`，且公鑰必須在 C 的 `keys.json`、簽章必須對當前 zip 成立。
- 已審核模組仍是 in-process，**不是沙箱**；審核與簽章只降低風險。
- `experimental` 只適合測試，不建議學校正式安裝。
